# PrismAgentKit V1.4 设计（上下文压缩 / 轨迹 / Model Profile）

- 状态：待评审
- 日期：2026-11-27
- 路线：1.4 是 1.x 最后一版；项目记忆放 2.0，Workflow 放 3.0
- 关联：MCP（V1.2）、Skills（V1.3）设计；上游参考 `agent-runtime-bff`、深度拆解的 DSH `dsh-compaction*` / `dsh-client-ui-trajectory` / `dsh-client-ui-model-selection`

## 0. 已确认的结论

1. **上下文压缩走 B（DSH-lite）**：先做确定性 tool 结果裁剪，再做结构化摘要；结果按 **checkpoint 表 + 保留原文** 存储。
2. **Trajectory 是独立页面**，与"执行详情"并存但职责分开：执行详情瘦身为"工具调用明细"，轨迹承载 Turn → Step → Tool、token、耗时、上下文事件。
3. **Model Profile 独立页面、多份档案、全局作用域**：切换后下一次请求起对**所有会话**生效；密钥只以环境变量引用（`api_key_env`）保存。
4. **压缩摘要请求复用当前激活的 Model Profile**，不单独配置摘要模型。
5. **压缩在 Engine 内、调用 ContextAssembler 之前执行**；`ContextAssembler` 保持同步纯函数，不承担网络请求与事务。应用最新 checkpoint 的方式是：Engine 把摘要构造为一条 `kind='checkpoint'` 的**合成消息**（不入 messages 表）置于消息列表最前，ContextAssembler 将其列为受保护单元。
6. **Provider 按 Run 解析**：Run 快照 `model_profile_id` + 模型/窗口/输出上限；Engine 在 Run 开始时解析一次 Provider 与 Assembler，运行中不切换。

## 1. 背景

1.x 到此为止：MCP 给了工具、Skills 给了方法，但长会话仍有两个硬伤——上下文满了只能**直接丢最旧的消息**（模型从此失忆），而且没有任何"模型每一步看了什么、花了多少 token"的可观测面；同时模型只能由 `.env` 固定，无法在页面上切档案。

V1.4 把这三件事一起补齐，并明确不把它做成三个互不相干的模块：压缩产生的事件会出现在轨迹里；轨迹里能看到每次压缩前后的 token；模型档案决定压缩摘要由哪个模型生成。

## 2. 外部参考（压缩）

| | 触发 | 压缩对象 | 摘要/保留 | 备注 |
|---|---|---|---|---|
| Claude（Engineering 博客） | 接近窗口 | 丢弃冗余 tool 输出，保留架构决策/未解 bug/实现细节 + 最近 5 个文件 | LLM 摘要重建上下文 | 另有 structured note-taking、sub-agent |
| Codex（`compact.rs` + prompts） | 自动 + `/compact` | 替换整段历史，保留 pinned/最近 user 消息（≤20k tokens），重注入 canonical context | 固定 `SUMMARY_PREFIX` + 结构化 handoff | overflow 重试 |
| Pi（`docs/compaction.md`） | `tokens > window - reserve(16k)` | 保留最近 20k tokens；切点只在 user/assistant 边界，不切断 tool 配对 | 7 段结构化摘要，重复压缩迭代更新；记录 read/modified files | overflow/length 一次重试 |
| DSH（`dsh-compaction*`） | tokenMeter 阈值 + overflow | **先 model-free 裁剪**（tool 结果头尾修剪、图片卸载），再摘要；保留 tail 比例/token | 8 段摘要、复用 system/tools 前缀命中 KV cache；checkpoint 消息；持久锁 | 工具配对平衡校验 |

落地选择：**先裁剪再摘要**（省 token 且不花 LLM），摘要结构取 DSH/Pi 的交集（8 段），存储取 checkpoint 表（原文不删，可回放）。

## 3. 目标

### 3.1 上下文压缩

1. 每次模型请求前，对历史 tool 结果做确定性 head/tail 裁剪（超阈值才裁剪，保留头尾、插入 `…(pruned)…` 标记）。
2. 裁剪后估算 token；超过输入预算的 85% 时，选最旧的一段生成结构化摘要，写入 `compaction_checkpoints`，并让后续请求从 `first_kept_message_id` 开始、摘要置于最前。
3. 重复压缩时把上一份摘要作为输入，增量合并。
4. provider 溢出/摘要失败时回退为纯裁剪 + 继续，不让 Run 直接失败；记录失败事件。
5. 会话页提供手动「压缩上下文」；运行中的 Run 不允许并发压缩。

### 3.2 Trajectory

6. 新增 Step 事件：`step.started` / `step.completed`（模型名、usage、tool_call_ids、耗时、stop reason）。
7. 新增只读轨迹接口，按 Turn（Run）→ Step → Tool 聚合，附 compaction / context trimmed 记录；旧 Run 从现有事件合成 Step 并标注"未记录 usage"。
8. 会话内新增「轨迹」Tab：账本 + inspector（输入/输出/usage/时间戳）；不做时间轴缩放与虚拟滚动。

### 3.3 Model Profile

9. `model_profiles` 表：名称、base_url、model、`api_key_env`、context window、max output；唯一 active。
10. 独立页面管理档案、测试连接、切换；切换全局生效，下一次请求使用新档案；运行中的 Step 保持不变。
11. 新建 Run 时快照档案（`runs.model_profile_id` + `model`）；Provider 按档案构造，密钥从环境变量读取，不明文入库。
12. 无档案时回退到 `.env` 配置（v1.3 行为），页面显示"环境配置（默认）"。

### 3.4 执行详情瘦身

13. 执行详情只保留工具调用列表（名称、参数、结果、状态、单次耗时）；移除 Run 状态块、错误块、审批提示、上下文事件。

## 4. 非目标

- 不做项目记忆（2.0）、不做 Workflow（3.0）。
- 不做图片/附件卸载（后续可加）；不做多模态 token 精确计量。
- 不做轨迹的时间轴缩放、虚拟滚动、跨会话搜索。
- 不做多 Provider SDK（仍走 OpenAI-compatible HTTP）；不做 OAuth/登录态。
- 不做按会话覆盖模型档案；不做档案级模型能力探测矩阵（仅"测试连接"一次 chat 请求）。
- 不做压缩的自动后台任务；只在请求前与手动触发时执行。

## 5. 反目标

- 物理删除/覆盖消息换取空间（不可回放，违反状态事实）。
- 在模型请求中途切换档案（同一 Step 内模型必须固定）。
- 把明文 API Key 写进 SQLite/日志/事件。
- 压缩后仍把旧消息发给模型（checkpoint 必须真正生效）。
- 轨迹与执行详情重复展示同一批工具行。

## 6. 约束

- SQLite 唯一数据库；迁移 `20261127_0007`（model_profiles、runs.model_profile_id、compaction_checkpoints）。
- 事件只追加；轨迹是投影，不新增第二套事实源。
- `ContextAssembler` 只做同步裁剪与预算校验；压缩的摘要请求、checkpoint 写入都在 Engine（有 UoW 与 Provider）中完成。
- checkpoint 以受保护的合成 `MessageKind.CHECKPOINT` 消息参与组装，绝不写入 messages 表，也不被裁剪。
- 摘要请求消耗 token，必须出现在轨迹（`compaction.completed` 带 usage）。
- 压缩必须保持 tool call/result 配对；同一 Run 内 Step 模型固定。
- 密钥只从环境变量读取；档案只存变量名。
- 配置项经 `pydantic-settings`（`PRISM_AGENT_KIT_` 前缀）。

## 7. 总体架构

```text
Model Profiles（SQLite，唯一 active）
        │  Run 创建时快照
        ▼
RunService ──► Run(model_profile_id, model) ──► Engine
                                                │
                         provider_resolver(run) ┴─► Provider（档案或 .env 回退）
                                                │
每个 Step： 加载消息 → 取最新 checkpoint（合成受保护消息）→ 裁剪 tool 结果 → 估算 token
            → 超阈值？ 摘要请求（同 provider）→ 写 checkpoint + 事件 → 重新加载/应用
            → ContextAssembler → provider.stream → step.completed(usage)
            → 若 provider 报 overflow：强制压缩一次后重试
                                                │
Trajectory API（投影 events + messages + tool_calls + checkpoints）──► 轨迹页
执行详情页（只读 tool_calls）
```

## 8. 上下文压缩设计

### 8.1 确定性裁剪（model-free）

- 作用对象：角色为 `tool` 的消息文本内容（JSON 字符串化后按字符计）。
- 触发：单条内容 > `compaction_prune_threshold_chars`（默认 8_000）。
- 规则：保留前 `head_chars`（默认 2_000）与后 `tail_chars`（默认 2_000），中间替换为 `\n…(pruned N chars)…\n`；只改发送副本，不改数据库。
- 按 Unicode code point 切分，避免拆坏多字节字符。
- **不裁剪**最近一条 tool 结果之外的配对结构（tool 消息整条保留，只是内容缩短）；不触碰 system/checkpoint。

### 8.2 Token 估算与触发

- 使用现有 `TokenEstimator`；有最近一次真实 usage 时按 `prompt_tokens / estimated` 校准估算值。
- 输入预算 = `run.model_context_window - run.model_max_output_tokens - safety_margin`（Run 创建时从档案快照；旧数据回退 `.env` 的 Settings）。Assembler 每个 Run 重建一次，`Engine` 在 Run 开始时解析，运行中不变。
- 触发阈值：`estimated > input_budget * compaction_threshold_ratio`（默认 0.85）。

### 8.3 选择摘要范围

- 从最旧开始，按"不可拆单元"（user 单条、assistant+其全部 tool 结果）累计，直到剩余 ≤ 保留目标。
- 保留目标 = `min(compaction_retain_tokens, input_budget * compaction_retain_ratio)`（默认 20_000 / 0.2）。
- 切点只在单元边界，绝不切开 assistant/tool；始终保留当前 Run 的用户消息。
- 可选范围为空（只剩最近单元）时不压缩，记录 `compaction.skipped`。

### 8.4 摘要请求与格式

- 复用当前 Run 的 provider/model（用户已确认）；`max_output_tokens` 取 `min(1500, 模型上限)`。
- 输入：被选中区间的序列化消息（tool 结果在摘要输入里再截到 2_000 字符）+ 上一份 checkpoint 摘要（如有）。
- 固定 8 段 Markdown：Primary Request and Intent / Key Technical Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step / Critical Context；要求保留精确路径、命令、错误串、标识符。
- 摘要结果包在 `<conversation_checkpoint>` 中，由 Engine 构造为**合成 user 消息**（`MessageKind.CHECKPOINT`）置于消息列表最前；不写入 messages 表，`ContextAssembler` 将其与 `skill_context` 一样视为**受保护单元**，任何裁剪都不会删除它。轨迹里显示为 compaction 记录。
- 重复压缩：新摘要必须合并旧 checkpoint 的事实，丢弃已过时内容。

### 8.5 存储与生效

`compaction_checkpoints`：

| 列 | 说明 |
|---|---|
| id | pk |
| session_id | 外键级联 |
| summary | 结构化摘要 |
| first_kept_message_id | 此后（含）的消息保留 |
| tokens_before / tokens_after | 估算值 |
| pruned_chars | 本次确定性裁剪省下的字符数 |
| created_at | 时间 |

- 组装上下文时取该会话最新 checkpoint：加载 `messages.id >= first_kept_message_id`，最前面注入 checkpoint 摘要；更旧消息不进入模型（但仍保留在库里，供轨迹/导出）。
- 手动压缩：`POST /sessions/{id}/compact`；要求无活动 Run，执行同一流程；无需要压缩的内容时返回 `{compacted: false, reason}`。

### 8.6 失败与溢出

- 摘要请求失败/超时（30s）：记录 `compaction.failed`，本次请求继续用"裁剪后 + 未压缩"的消息；不写 checkpoint。
- provider 返回 context overflow（新增端口字段/错误码 `CONTEXT_OVERFLOW`）：同一次请求内允许**一次**强制压缩重试（阈值忽略），仍失败则 Run 失败并保留错误。
- 手动压缩失败返回 502 类错误，不写半成品。
- **与既有兜底的关系**：`ContextAssembler` 保留 100% 预算时"丢最旧非保护单元 + `context.trimmed` 事件"的兜底；压缩在 85% 触发，是优先路径。若压缩后仍超 100%，才由 Assembler 兜底；只剩受保护单元仍超预算时按 `CONTEXT_BUDGET_EXCEEDED` 报错。

## 9. Trajectory 设计

### 9.1 事件扩展

- `step.started`：`{step_index, model, model_profile_id?}`。
- `step.completed`：`{step_index, usage: {prompt, completion, total}, duration_ms, tool_call_ids, finish_reason}`；失败时 `step.failed` 带 error_code。
- `compaction.started/completed/failed/skipped`：`{checkpoint_id?, tokens_before, tokens_after, pruned_chars, usage?, error?, reason?}`。
- `context.pruned`：`{pruned_chars, pruned_count}`，仅在某一 Step 实际发生确定性裁剪时记录（每 Step 至多一条）。
- 现有 `assistant.completed`、`tool.*`、`context.trimmed` 保留；`assistant.completed` payload 增加 `step_index` 关联（向后兼容：可选）。
- 端口扩展：`ModelResponse` 增加 `finish_reason: str | None`；Provider 在 HTTP 400/422 且响应表明上下文超限时抛 `CONTEXT_OVERFLOW`。

### 9.2 投影接口

`GET /sessions/{id}/trajectory?limit=&before=`：

```json
{
  "turns": [{
    "run": {"id","status","input_text","created_at","finished_at"},
    "steps": [{
      "index": 0, "model": "...", "usage": {"prompt_tokens":0,"completion_tokens":0,"total_tokens":0},
      "duration_ms": 1200, "stop_reason": "stop", "assistant_message_id": 12,
      "tools": [{"call_id","tool_name","status","duration_ms","input","output"}]
    }],
    "compactions": [{"id","tokens_before","tokens_after","created_at"}]
  }]
}
```

- 新 Run 直接由 step 事件投影；旧 Run 无 step 事件时，用 `assistant.completed` + 工具事件合成一个 Step，`usage=null` 且 `legacy=true`。
- `limit` 默认 50 个 Turn，`before` 游标按 Run 创建时间；V1.4 只做"加载更早"按钮，不做虚拟滚动。

### 9.3 UI

- 会话内第三个 Tab「轨迹」，独立路由 `/sessions/:id/trajectory`；AppShell 的 Tab 判定从两态扩为三态（`session | execution | trajectory`），消息列表「查看执行」仍指向执行详情，轨迹入口在 Tab。
- 账本按 Turn 分组；Turn 头显示状态与耗时；Step 行显示模型、tokens、耗时；Tool 行嵌套在 Step 下，显示名称、状态、耗时；compaction 行独立展示"上下文已压缩：tokens_before → tokens_after"。
- 点行打开 inspector（右侧/抽屉）：原始输入、输出、usage、时间戳；tool 行显示参数与结果。
- 运行中跟随尾部；页面每 2 秒重新拉取一次（仅当会话存在非终态 Run），终态后停止轮询；无时间轴缩放、无虚拟滚动（>50 Turn 用"加载更早"）。

## 10. Model Profile 设计

### 10.1 表结构

`model_profiles`：`id, name(unique), base_url, model, api_key_env, context_window, max_output_tokens, created_at, updated_at, is_active`；`is_active` 用部分唯一索引保证至多一条。

- 校验：`base_url` http(s)、`model` 非空、`api_key_env` 形如环境变量名、context/max 正数且 max < context。
- 档案只存环境变量名；API 不回显变量值。
- 启动时若存在 active 档案则使用；否则回退 `.env` 配置并在 UI 显示"环境配置（默认）"。

### 10.2 生效与快照

- `activate(id)` 更新唯一 active；影响之后创建的所有 Run（含历史会话的下一句）。
- `RunService.create` 读取 active 档案：`runs.model_profile_id`、`runs.model`、`runs.model_context_window`、`runs.model_max_output_tokens` 写入快照；Provider 由 `ProviderFactory(profile_id)` 构造（LRU 缓存，档案更新时失效）。
- `Engine` 接受可选的 `provider_resolver(run)` 与 `assembler_factory(run)`；未注入时沿用构造时传入的单例（保证现有测试不变）。容器在 Worker 构建时注入 resolver，Run 开始时解析一次。
- 运行中的 Run 用启动时解析的 provider，不受切换影响；轨迹 Step 行显示实际模型。
- 启动校验：存在 active 档案时不再强制要求 `MODEL_*`（校验档案字段）；无档案时保持 v1.3 的环境配置校验。
- 标题生成与 `probe`：标题服务按"当前 active 档案"每次解析 Provider；`probe` 直接用目标档案构造一次性 Provider，不依赖 active。
- 密钥缺失/变量未设置：创建 Run 前返回 `MODEL_PROFILE_INVALID`（422），不创建 Run。

### 10.3 接口与 UI

- `GET /model-profiles`、`POST`、`PATCH /{id}`、`DELETE /{id}`、`POST /{id}/activate`、`POST /{id}/probe`。
- `probe`：用该档案发一次最小 chat 请求（max_tokens=8），返回 `{ok, latency_ms, error?}`。
- UI 独立导航页「模型」：档案列表（active 标记）、表单（名称/base_url/model/api_key_env/context/max）、测试连接、切换；切换后提示"下次请求生效"。

## 11. 执行详情瘦身

- `RunInspector` 只保留：工具调用列表 + 每项参数/结果/状态/耗时；标题「工具调用」。
- 移除：Run 状态块、错误块、审批提示（审批在会话页）、上下文/步骤信息。
- 无工具时显示"本次运行没有工具调用"。
- `ToolCallCard` 保留并复用；轨迹页不复用该组件（自己的行渲染）。

## 12. 数据模型与迁移

迁移 `20261127_0007`：

```sql
CREATE TABLE model_profiles (...);
CREATE UNIQUE INDEX ux_model_profiles_one_active ON model_profiles(is_active) WHERE is_active = 1;
ALTER TABLE runs ADD COLUMN model_profile_id TEXT REFERENCES model_profiles(id) ON DELETE SET NULL;
ALTER TABLE runs ADD COLUMN model_context_window INTEGER;
ALTER TABLE runs ADD COLUMN model_max_output_tokens INTEGER;
CREATE TABLE compaction_checkpoints (...);
CREATE INDEX ix_checkpoints_session_created ON compaction_checkpoints(session_id, created_at);
```

`runs` 增加 `model_profile_id`（可空，兼容旧数据）；`Run` 领域模型同步。

## 13. 错误码

`MODEL_PROFILE_NOT_FOUND`、`MODEL_PROFILE_INVALID`、`MODEL_PROFILE_IN_USE`（删除 active 时需先切换）、`COMPACTION_FAILED`、`COMPACTION_BUSY`、`CONTEXT_OVERFLOW`（Provider 端口映射）、`TRAJECTORY_UNAVAILABLE`。

## 14. 测试

- 裁剪：超阈值头尾保留、Unicode 不拆坏、tool 配对不变、短内容不动。
- 阈值/选择：85% 触发、保留目标、不切 tool 组、无可压缩范围跳过。
- 摘要：8 段格式、迭代合并、失败回退不写 checkpoint、溢出强制重试一次。
- checkpoint 生效：压缩后请求只带 first_kept 之后消息 + 摘要；摘要作为 CHECKPOINT 合成消息**不被裁剪**；原文仍在库；手动压缩 busy 保护。
- 兜底顺序：85% 压缩 → 仍超 100% 时 Assembler 丢最旧并记 `context.trimmed`；只剩受保护单元报 `CONTEXT_BUDGET_EXCEEDED`。
- Provider 解析：有档案时按 Run 快照构造；运行中切换档案不影响当前 Run；启动校验在"有 active 档案"时不要求 MODEL_*。
- 溢出重试：Provider 抛 `CONTEXT_OVERFLOW` 时强制压缩一次并重试；仍失败则失败并记录。
- 轨迹：新 Run 的 Step/Tool 投影、旧 Run legacy 合成、compaction 行、limit/before 分页。
- 档案：CRUD、唯一 active、切换后新 Run 快照、运行中不受影响、密钥缺失 422、probe。
- UI：执行详情只渲染工具、轨迹 Tab 渲染与 inspector、模型页切换与测试连接。

## 15. 阶段与规模

项目级，分 4 阶段：

1. **档案与 Provider 路由**：表/迁移、CRUD/activate/probe、ProviderFactory、Run 快照。
2. **压缩内核**：裁剪器、token 估算与选择、摘要器、checkpoint、组装集成、手动压缩、失败回退。
3. **轨迹数据与接口**：step/compaction 事件、投影 API、旧 Run 兼容。
4. **UI**：轨迹 Tab、执行详情瘦身、模型页、会话压缩入口；收尾文档与 1.4.0。

规模估计：后端 1_600–2_000 行（含测试），UI 700–900 行。

## 17. 风险

- 摘要质量：prompt 固定 8 段 + 保留精确标识符；用真实长会话回归。
- 压缩与 Step 事件顺序：必须先裁剪/摘要再发 step.started？——设计为 step.started 在组装前、压缩在组装内并发事件；轨迹按事件时间排序展示，不依赖序号。
- 档案切换让历史会话换模型：模型能力差异可能导致行为变化，轨迹会显示实际模型，便于排查。
- 密钥全部依赖环境变量：部署时需保证后端进程能读到；缺失时给明确 422。
- 迁移一次性新增三张/三列：升级脚本要可回滚，旧会话不受影响。
