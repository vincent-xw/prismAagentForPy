# PrismAgentKit Core UI 设计

- 日期：2026-11-22
- 状态：2026-11-22 用户已确认设计及计划并授权实施；结果与限制见验收记录
- 当前分支：`feat/python-ui-separation`
- Backend 参考：`feat/python-agent-core`，本次检查提交为 `5a8f897`
- 首期目标：围绕 Python Agent Core 建立可用的对话工作台和可扩展的 UI 基础

## 1. 已确认的方向

- 保留浅色、深色两套主题；浅色去掉旧版大面积的绿色倾向，深色重新设计。
- UI 可以重新组织，不要求与 Node.js Runtime 一比一复刻。
- 引入样式与组件基础，降低开发成本，同时保留自主设计和修改组件的能力。
- 重新考虑抽屉的职责，避免各种功能都依赖侧边抽屉。
- 旧版引导弹窗中有价值的体验可以保留，步骤必须符合当前 Backend 能力。
- 首期对接 Core 已有能力，不一次性迁移旧 Runtime 的全部功能。
- 保持前后端工作边界：UI 位于 `ui/`，Python 后端位于 `backend/`；跨层协议变更必须同时说明两端影响。

以下技术组合、信息架构和交互方向已随整体设计确认；具体色值继续通过原型和视觉验收调整。

## 2. 已核对的 Backend 边界

已阅读 Backend 的技术设计、实施计划，以及 HTTP 路由、DTO、鉴权与应用装配源码。接口实现是接入时的核对依据，文档示例不能替代实际契约。

### 2.1 首期可以承接的能力

| Backend 能力              | UI 行为                                          |
| ------------------------- | ------------------------------------------------ |
| 创建、列出、查询 Session  | 创建会话、浏览会话列表、打开会话                 |
| 查询 Session Messages     | 展示持久消息，刷新后恢复历史                     |
| 创建 Run                  | 发送输入，等待异步执行                           |
| 查询 Run                  | 展示当前状态、结果、错误及执行信息               |
| SSE 文本与事件            | 实时输出、运行状态和工具事件展示                 |
| 取消 Run                  | 请求停止，并等待服务端状态确认                   |
| 查询注册工具及 Schema     | 展示实际工具目录与说明；允许真实的空列表         |
| 远端工具等待与回填协议    | 展示等待外部宿主的状态，为未来宿主模块留接入边界 |
| 健康检查与 API Token 鉴权 | 服务可达性检查、访问验证、连接错误处理           |

同一 Session 只能存在一个活动 Run。UI 应反映此约束，同时处理 Backend 返回的 `409`，不能只依赖禁用按钮保证正确性。

### 2.2 本次不建立的界面能力

- MCP 服务管理、凭据配置和授权。
- Workspace、目录选择、索引、RAG、设备管理与浏览器执行。
- 多 Agent、Workflow、Skills 管理与任务平台集成。
- 模型档案、模型切换、模型密钥保存和模型发现。
- 会话删除、重命名、置顶、收藏；当前没有相应 HTTP 接口。
- 工具注册、启用、禁用和任意工具执行；`GET /tools` 是发现接口。
- 手工填写 JSON 的远端工具回填表单。回填接口首先服务外部宿主，不自动转化为普通用户操作。
- 全局运行管理台；当前没有列出全部 Run 的接口。

默认应用装配使用空的工具注册表。测试中的 `echo`、`wait_for_host` 不代表默认生产实例已经提供这些工具。空工具状态必须明确显示，不能构造工具卡片。

## 3. 方案比较与推荐

### 方案 A：极简对话页

会话与消息是全部主界面，运行和工具信息都折叠在消息内。

- 优点：首期开发量小，使用路径短。
- 代价：Core 已有的状态、错误和工具等待信息较难集中查看；后续增加能力时容易继续堆叠在对话内。

### 方案 B：对话工作台 + 按需执行详情 + 独立设置页

默认专注对话，执行详情需要时在工作区内展开；连接和外观配置进入独立设置页。

- 优点：符合当前 Core 的对话主流程，也能查看运行事实；长期功能有稳定归属，不需要不断新增抽屉。
- 代价：需要先明确应用壳、页面路由和执行详情的边界。

### 方案 C：执行控制台优先

以 Run 列表、工具记录和状态面板为主，对话作为其中一个视图。

- 优点：适合开发调试与集中检查执行。
- 代价：普通对话路径更重；完整运行列表还需要 Backend 新增查询能力。

**推荐方案 B。** 首期只建立会话与设置两个一级入口，工具与执行信息依附当前会话和 Run。后续模块具备真实后端支持后，再注册自己的页面与导航。

技术组合建议使用现有 Vue 3 + TypeScript + Vite，增加 Tailwind CSS 和按需引入的 shadcn-vue 基础组件。组件源码在项目内维护，统一由 Prism 主题变量控制外观；业务界面自己组织。

## 4. 视觉方向

### 4.1 共同原则

- 背景与面板采用中性色，品牌色只用于主要操作、选中态和重点信息。
- 成功色只表达成功状态，不再承担整个浅色界面的底色。
- 深色通过页面、面板、悬浮层的明度差区分层级，避免大面积纯黑或有色背景。
- 深浅主题共享布局、组件尺寸和语义，分别定义颜色值。
- 页面留白与文本层级优先，不以大量卡片、粗边框或装饰渐变制造层级。

### 4.2 建议色板

这些数值是待视觉验证的设计起点，不是已验收的最终色值。

| 语义             | 浅色：中性灰白 | 深色：石墨灰 |
| ---------------- | -------------- | ------------ |
| 页面背景         | `#F6F7F9`      | `#111318`    |
| 主面板           | `#FFFFFF`      | `#191C23`    |
| 次级面板         | `#F0F2F5`      | `#22262F`    |
| 主要文字         | `#18212F`      | `#EAECF2`    |
| 次要文字         | `#596477`      | `#A2AABA`    |
| 默认边框         | `#DCE1E8`      | `#343B48`    |
| 品牌与主要操作   | `#4F46E5`      | `#A6A1FF`    |
| 主要操作悬停     | `#4338CA`      | `#B8B3FF`    |
| 品牌浅底         | `#EEECFF`      | `#282344`    |
| 主要操作上的文字 | `#FFFFFF`      | `#17132D`    |

成功、警告、错误和信息使用独立语义变量，并同时提供文字或图标表达。对比度、禁用态和交互态在原型及组件验收时检查，不仅检查上述静态色板。

### 4.3 主题与样式组织

- 主题提供页面、面板、文本、边框、品牌、状态、焦点、间距、圆角和控件尺寸等语义变量。
- 将语义变量映射到 Tailwind 和 shadcn-vue 使用的主题；不维护两套互不关联的颜色。
- 页面主要使用 Tailwind 组织布局与响应式。
- 公共控件通过组件的 `variant`、`size` 等明确接口表达差异，避免每处复制长串控件类名。
- 复杂业务排版可以保留组件内样式，不要求所有 CSS 都改成工具类。
- 中文优先使用系统字体；正文采用舒适密度，技术 ID 和结构化数据局部使用等宽字体。
- 支持浅色、深色和跟随系统；外观偏好保存在浏览器，在首次绘制前应用。

## 5. 页面与容器职责

### 5.1 会话工作台

- 左侧为会话列表和“新建会话”，允许折叠，不作为通用功能抽屉。
- 主区为当前会话、消息流、输入区和明确的运行状态。
- 顶部只保留当前会话信息、连接状态与必要操作，减少多组管理按钮。
- 对话中的工具摘要可展开；查看完整执行信息时，按需展开工作区内的详情区域。
- 详情区域属于当前会话和 Run，不叠加遮罩，也不阻断继续阅读对话。
- 消息加载、空会话、输出中、等待外部工具、已停止和错误都有明确状态。
- 工具参数与结果按实际返回展示；普通用户不必阅读原始事件 JSON。

### 5.2 执行详情

- 展示当前 Run 的状态、开始与结束时间、模型、执行步数和错误信息。
- 展示实际发生的工具调用及其状态、结果和错误。
- 等待远端工具时使用“等待外部工具结果”等准确说明，不误称为用户审批。
- 点击停止后先表现为正在请求或等待停止确认，不能提前显示已取消。
- 断线属于连接状态，不等同于 Run 失败；查询和重连后以 Backend 状态恢复。
- 不添加没有接口支撑的“重新执行”“继续”“批准”等操作。

### 5.3 设置页

首期只包含连接、外观和当前服务的只读信息。

- API 基路径来自显式前端配置；开发代理目标沿用 `PRISM_UI_API_TARGET`。
- 连接区域展示当前服务路径，输入或清除本地 API Token，并提供访问验证。
- Token 建议保存在当前标签页的 `sessionStorage`，刷新后可继续使用，关闭标签页后清除；不写入构建变量或长期 `localStorage`。
- 模型密钥与模型环境变量由 Backend 管理，本页不提供虚假的保存表单。
- 工具目录按实际 `GET /tools` 返回展示；无工具时说明尚未注册。
- 设置是可直接到达的页面，离开时保留当前会话，不把设置层层嵌入抽屉。

### 5.4 弹窗、抽屉和浮层

| 容器           | 职责                                       |
| -------------- | ------------------------------------------ |
| 页面           | 会话、设置，以及未来可以独立导航的长期功能 |
| 工作区内详情   | 当前 Run 与工具的上下文信息                |
| 居中弹窗       | 简短输入、必要确认                         |
| Popover / 菜单 | 少量即时选择与操作                         |
| 窄屏 Sheet     | 会话导航或当前执行详情的响应式承载         |

桌面不以抽屉承载所有管理功能。窄屏允许把桌面的导航与详情转为 Sheet，但不允许多层 Sheet 相互套叠。

## 6. 连接入口收敛到设置页

旧 Runtime 的六步引导依赖模型配置、Workspace、设备与 MCP 等接口，新 Core 没有这些能力。单独为“连接服务”和“验证访问”制作首次弹窗会重复设置页已有的功能，因此不设首次引导弹窗。

连接流程：

1. 未连接时，工作台显示“连接服务后开始对话”，并链接到设置页。
2. 设置页展示当前服务路径，可单独执行健康检查。
3. 输入 API Token 后调用受保护查询验证访问，明确区分 `401`、协议错误和网络失败。
4. 验证成功后，返回工作台即可使用，不再经过额外确认步骤。

约束：

- 健康检查成功只证明服务可达，不表示 Token 有效、模型调用成功或工具可用。
- 首期没有模型探测 API，不把健康检查包装成模型验证，也不自动发送付费模型请求。
- 已验证、未验证和失败分别显示，不用“跳过”伪装成功。
- 主题和 Token 是前端偏好，不调用不存在的 Backend 设置接口。
- 访问失败可在设置页重新验证，不丢弃用户尚未发送的输入。

## 7. 接入契约与状态恢复

### 7.1 分离持久事实与临时输出

- Session、Run 和 Messages 的响应作为持久事实。
- `message.delta`、`reasoning.delta` 作为临时输出处理，不冒充完整持久消息。
- `assistant.completed` 后读取持久消息，替换对应的临时输出，避免重复追加。
- 持久事件可重放；按事件 ID 去重，并按 Run 隔离订阅与状态。
- SSE 重连携带 API 鉴权和 `Last-Event-ID`；服务端终态关闭不触发无限重连。
- 切换会话时管理订阅生命周期，防止上一会话的增量写入当前界面。
- 消息、Markdown 和工具内容不能作为未经处理的 HTML 插入页面。

### 7.2 工具详情的数据来源与承诺范围

首期不要求 Backend 新增接口。工具详情由当前 Run 的持久事件和会话中的持久消息关联得到，不假设可以调用独立的 ToolCall 查询接口。

| 展示内容                        | 现有数据来源                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------- |
| 调用 ID、工具名、执行方式、参数 | `tool.requested` 的 `call_id`、`tool_name`、`execution_mode`、`input`           |
| 成功事实                        | `tool.completed`，不通过结果 JSON 的形状猜测成功或失败                          |
| 工具输出                        | 完成事件的 `message_id` 对应的持久 Message；同时校验 `run_id` 和 `tool_call_id` |
| 失败事实与说明                  | `tool.failed` 的 `error_code`、`error_message` 及关联的持久工具消息             |
| 已取消                          | `tool.failed` 且 `error_code` 为 `RUN_CANCELLED`                                |
| 已过期                          | `tool.expired`，当前远端超时对应 `REMOTE_TOOL_TIMEOUT`                          |
| 进程中断等异常闭合              | Backend 写入的工具失败事件及关联消息；不根据 Run 终态给全部工具统一改状态       |

接收到关联完成事件后刷新持久消息；历史 Run 在用户查看详情时有限重放持久事件，避免进入会话就为全部历史 Run 建立订阅。活动 Run 的消息展示与详情共用同一个事件订阅和投影。

只收到 `tool.requested` 时显示“已请求，等待结果”等已确认事实。当前没有工具开始执行事件，首期不承诺精确区分单个本地工具的 `pending/running`，也不显示缺少来源的执行耗时或截止时间。

缺少关联事件或消息时显示详情未完整取得，并允许重新读取；不补造参数、结果或终态。工具参数和错误详情按需展开，主对话只显示简要信息。

### 7.3 刷新后恢复

- 路由携带 Session ID，恢复时重新查询会话与消息。
- 已持久化消息包含 `run_id`，可据此查询相关 Run，而不是假设存在会话运行列表接口。
- 前端最近的 Run 引用只能作为查询线索，状态仍由 Backend 返回确认。
- 刷新后从待查看 Run 的持久事件起点重建投影；页面内已有完整投影的断线重连才携带其最新已处理游标。不能只恢复游标而丢失游标之前的工具信息。
- 最终消息用于恢复断线期间缺失的文本；Core 不承诺重放每个临时增量。
- 活动 Run 的发现与恢复需要覆盖页面刷新、切换会话和进程重启后的实际数据，不仅验证当前内存中的运行。

### 7.4 已发现的契约对齐项

- Backend 设计中的 SSE 示例使用 `evt_42`，实际路由只接受非负整数 `Last-Event-ID`，序列化也输出整数的字符串。UI 按实际实现接入；文档差异另行交由 Backend 维护。
- Session 视图没有 `active_run_id`，也没有查询 Session Runs 的接口；恢复需要利用已持久消息中的 Run 引用，并验证边界，不能凭空增加 DTO 字段。
- 没有读取或修改模型配置的 API，UI 不声称能显示或保存完整服务配置。
- 此分支仍是旧 Backend 脚手架。正式联调需要用户合并 Core，或显式连接 Core 工作分支启动的服务；不能以脚手架健康检查通过代替 Core 接入验收。

## 8. 扩展方式

建议按以下边界组织 UI，具体文件在实施计划中确定：

- `app/`：应用入口、路由、应用壳、主题和模块注册。
- `components/ui/`：项目维护的基础组件与变体。
- `features/sessions/`：会话、消息与输入。
- `features/runs/`：执行状态、事件订阅与详情。
- `features/connection/`：连接、鉴权、访问验证与引导。
- `features/settings/`：外观及设置页面组织。
- `lib/api/`：按实际 HTTP 协议定义的 DTO、请求和 SSE 传输。

后续 MCP、Workspace 等能力各自新增模块，注册路由与导航，按需复用控件。首期不引入伪能力接口、通用动态表单引擎或空白功能导航。

API DTO 与界面状态分离：协议适配集中处理，业务组件不读取 Node.js 旧 DTO，也不直接处理传输分片。

## 9. 交付顺序

1. 确认本设计方向，并用深浅主题与关键状态原型验证视觉和信息架构。
2. 接入 Tailwind 与所需基础组件，建立主题、应用壳和前端路由。
3. 完成设置页连接、会话与 Run 的最小实际链路。
4. 补齐工具详情、断线恢复、取消与错误状态，进行 Core 联调验收。

原型可以使用明确标识的演示数据，产品接入不能在请求失败时自动回退到 Mock。每个阶段都保持可检查的范围，不顺带迁移旧 Runtime 的其他功能。

## 10. 验收重点

- 深浅主题、跟随系统、首次加载、键盘焦点、状态文字和禁用态一致。
- 桌面主流程不依赖层层抽屉；窄屏导航与详情仍可操作。
- 创建会话、连续发送、读取历史、刷新恢复和多会话切换使用真实 Core。
- 同一会话活动 Run 冲突、取消等待、模型失败和工具等待有准确反馈。
- 事件重放不重复消息；临时文本被持久消息替换；终态停止重连。
- `401`、`404`、`409`、服务不可达和非法响应分别处理，不伪造成功或字段默认值。
- 空工具目录是真实空状态，不展示测试工具或尚未迁移的导航。
- UI 的 lint、format、typecheck、build 通过；业务状态与传输逻辑补充必要测试。
- 不修改 Backend 分支、Python 源码或后端目录结构。
